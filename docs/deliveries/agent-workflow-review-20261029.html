WORKFLOW REVIEW / 01

先看结论与真实边界

产品定位纠正：工作台给开发者和 Agent 操作真实项目，主线是文件、代码、Git、运行、接口、数据和交付。各 Agent 用自身客户端的定时任务唤醒自己；工作台不成为工人调度总控。

现有注册、抢单和执行回写可继续复用；HTML 交付表与审核表均已存在。工作台前后端的交付与验收接口仍待接通。

本报告把「已核实的现状」与「目标流程」放在一起，供卓橦逐项审视。表结构来自本次只读查询；代码与引导基于当前本地仓库，不代替运行中的服务验收。

现有基础

TiDB 统一任务源，自命名注册、心跳、指定任务与公共池认领、执行记录、PR 回写。

刚补齐的表

task_deliveries 保存 HTML 正文；task_delivery_reviews 追加人工验收意见。

待完成的连接

认证提交、版本与幂等事务、跨机器读取、隔离预览、审核后任务流转。

首个闭环：Agent 完成任务 → 按 Skill 生成 HTML → 入库取得回执 → 工作台打开准确版本 → 本人通过或退回。

本报告未认领真实任务、写入报告数据、操作排程或发布应用。下文时间、限额与接口中标为“建议”的内容尚未生效。

WORKFLOW REVIEW / 03

Agent 自己的初始化与定时任务

各客户端自行管理唤醒方式，所有客户端统一醒来后的协作协议。

首次接入

  1. 先发现本客户端已有身份与私有配置，恢复原绑定，不覆盖其他客户端。
  2. 首次才自选唯一名字、注册并读回；自报名字不是认证。
  3. 使用该客户端自己支持的原生自动化或定时任务入口，核对所属会话、身份、触发规则和任务标识。
  4. 已有配置复用或更新，不重复创建；不支持自动化就明确报告限制。
  5. 分别确认保存、启用和实际触发，不把手动心跳说成自动唤醒。

醒来以后统一做什么

核对身份 → 心跳 → 读通知 → 恢复或按权限领单
进入项目开发 → 实现与调试 → 验证 → HTML 交付与回写 → 结束本轮

工作台提供项目开发现场。Agent 的定时任务在各自客户端创建，不由工作台统一安装、守护或调度；已有脚本 runner 只是兼容选项。

原生自动化可能先启动模型再检查队列，因此不能承诺所有客户端无单零模型调用。只有具备模型外预检查的兼容 runner 才可能实现该优化。

间隔、生命周期和运行前提按实际宿主确认；关闭工作台不会决定其他 Agent 客户端的定时器是否继续。当前没有逐机核验现有自动化配置。

WORKFLOW REVIEW / 04

接单、执行与会话交接

现有公共池认领已支持。具名任务优先，按所选 runner 检查 busy、needs_you、暂停／改派通知，再原子认领；抢输不算拥有任务，不得执行对方的单。

情形处理方式
有 current 或未完成的执行先恢复／确认原进程，不重复领单
doing 且有真实 PR，已完成执行交接sidecar 可释放 current，让任务留给人工审核；按当前适配器实际规则处理
公共池未分配 todo允许的空闲客户端原子抢单；指定任务优先
needs_you／暂停／改派先执行相应门禁，不靠心跳继续推进
同一产品仓多个任务延续同仓单工人约束；需核查是否已有可执行的仓级互斥，不能只靠提示词
验收要求改变重读 acceptance 与版本；未按新版验证，不提交为新版完成

每次工作都应留下的恢复包

任务 ID、实际验收版本、代码仓和基准提交、当前分支／commit、已完成步骤、失败证据、未完成项与下一步。状态由数据库记录；代码与原始成果保存在相应仓库，HTML 汇总可读结论。

开工先核对实际基线。本轮曾因未同步代码，把已有抢单误判为缺失；这类错误应通过入口校验和版本记录减少。

共享 worker.py 与 sidecar 不是完全相同的实现。正式整合前必须列出能力差异，不能把其中一份的通知、PR 交接语义假设为所有客户端都具备。

WORKFLOW REVIEW / 05

默认交付：Skill → HTML → 数据库

使用你的 tongyun-document Skill 生成自包含 HTML：内嵌样式，正文可以离线阅读，必要图片计入报告大小，原始代码和大型二进制仍保留。报告不能含口令或未经授权的私有数据。

报告必须包含为什么需要
目标与验收版本回答这次究竟按什么要求完成
结果与影响范围直接说明完成内容与变化
原始成果、代码 commit、PR读者能回到准确产物，而非只有描述
实际验证方法、结果与证据把运行事实与 Agent 自述分开
未测项、限制和遗留问题防止“看起来漂亮”掩盖未完成
下一步与待本人决定事项让验收者知道如何处理

提交事务（待实现）

  1. 从认证上下文确定工人身份，锁定任务并校验归属、当前验收版本、停止通知与执行关联。
  2. 查询任务＋request_id。相同请求重试返回原记录；同键不同完整内容拒绝。
  3. 服务端分配 version，计算 UTF-8 正文 SHA-256 和字节数，插入 task_deliveries。
  4. 追加最终 task_runs 与必要通知，绑定本次交付的 run_id；原子提交后返回 ID、版本和校验值。
  5. 取得成功回执后交接 current。超时或断网先查询幂等回执，不盲目创建第二份。

建议 HTML 正文上限 2 MiB、JSON 请求上限 4 MiB，均应可配置。MEDIUMTEXT 的容量上限不能代替 API、连接包大小和预览内存限制。

仅有正文 hash 不足以比较完整幂等请求：task、run、验收版本、标题、摘要等也需一致。task_deliveries 的 created_by 由认证身份确定，不能相信调用者随意填写。

WORKFLOW REVIEW / 06

审核、返工与三套状态

工作台先取分页交付摘要，点开时才读 HTML 正文，避免把每篇大报告都拉进列表。默认静态隔离预览，不向 HTML 暴露 Tauri IPC、工作台凭据或网络访问。

需要交互计算器时，使用另行验证的独立预览模式；静态报告和可执行内容的权限不同。原文保留，预览净化不覆盖原稿。

状态所在表示什么不能推出什么
tasks.status任务整体状态，如 todo / doing / blocked / donedoing 不证明 Agent 当前仍在工作
workers.current_task_* 与 task_runs执行槽位、每次尝试及结果清空 current 不证明交付通过；run done 不是本人批准
task_delivery_reviews.verdict对 delivery_id 精确版本的 accepted / changes_requested旧版通过不能自动批准新版或新的验收标准

通过

本人打开当前交付和证据，提交审核。服务端验证负责人身份、最新有效交付、验收版本和并发条件，追加审核行，并在同事务中推进任务状态。旧版本可读，不应被当成当前任务的通过依据。

要求修改

意见必填，审核绑定原交付 ID，通知进入工人收件箱。原报告不覆盖，返工后追加 V2／V3。工人可能已在做别的任务，退回不能直接抢占或覆盖其 current；应按队列和调度规则重新安排。

必须定清：新人工验收规则只对迁移后接入的交付闭环生效。旧适配器已有的 finish／done 和历史任务不得无条件重解释或回写。

WORKFLOW REVIEW / 08

我建议你重点挑这八处

下面是差距清单，不是“发现了八个线上故障”。每项标注了证据类型，避免把设计建议说成已证实的 bug。

P0已确认缺口

交付与审核服务还未接通

两表存在，正式 Studio Agent 页仍为本地快照。

补法：实现认证写入、查询和审核接口，跑一笔隔离的跨客户端闭环。

P0迁移风险

执行完成与人工验收语义可能冲突

旧适配器可 finish→done，新增方案要求本人审核。

补法：明确适用范围与兼容开关；防止旧 runner 绕过新审核。

P0设计要求／需验证

身份授权不能靠自选名字

workers 有 assignee 和 machine，无独立客户端认证字段。

补法：服务身份绑定与私有凭据校验；自命名不等于拥有同名账号。

P0需实现验证

并发提交／审核与重试

唯一键已有；当前表本身不阻止旧版审核或冲突结论。

补法：锁任务、校验最新版本、完整幂等比较；双人并发只能有一个有效流转。

P1已确认整合风险

不同入口的规则存在差异

worker.py、sidecar 和旧引导包含不同周期与交接细节。

补法：能力发现与适配器合同测试；不要在 UI 复制第三套规则。

P1待专项核查

旧执行复活与同仓并发

已见原子认领；本轮未完成工具端执行权隔离与仓级互斥审计。

补法：先保持人工接管，核验租约代次及 Git/发布写入口；加真实故障演练。

P1设计要求／需验证

HTML 报告会执行不可信内容

报告由 Agent 生成，可能含脚本、外链或诱导文字。

补法：隔离 origin、IPC、网络与导航，静态优先；原文与预览分开。

P1待专项盘点

客户端自动化重复与成本边界

各客户端自己的定时任务、宿主条件与消耗本轮未逐机核查。

补法：在每个客户端内复用其有效自动化配置；按实际机制记录模型消耗，增加预算和失败退避。

端到端验收：这些情形必须跑通

测试情形预期结果
双工人同时抢一单只有一个成功；失败方不执行、不产生成功认领记录。
同一个工人被重复唤醒互斥锁与数据库门禁都有效，不拿第二单。
请求成功但客户端没收到回执按原 request_id 重试，只得到同一份交付。
相同 request_id 携带不同正文或版本拒绝冲突，不覆盖原交付。
两人同时通过／退回同一交付最多一个有效流转；另一方看到明确冲突并重新读取。
审核时新交付或新验收版本已经产生旧审核请求拒绝，展示需要重新核验的版本。
退回时原工人已领取新任务不覆盖其 current；返工排队并保留通知。
执行中暂停／改派停止旧工作与写入，保留检查点；不单凭机器心跳接管。
报告含联网脚本、表单或 Tauri 调用预览不联网、不获得 IPC，不触发任何自动审核。
任务引用的代码／报告只在工人本机明确待共享，不谎称其他机器可访问。

测试使用隔离任务和获授权账号，不用真实发布或生产业务数据试错。每条保留输入、准确版本、数据库前后状态、退出码与证据；未执行则明确写未执行。

实现顺序

  1. 先接 HTML 提交、读回和静态预览：跨客户端看同一 delivery_id。
  2. 接审核事务与任务／通知流转：通过、退回、旧版与并发冲突。
  3. 完善各客户端的初始化引导：复用原生定时任务，分别核验保存与实际触发；Studio 保持项目开发主线。
  4. 再补租约、工具写入隔离、仓级互斥、预算与恢复演练。
